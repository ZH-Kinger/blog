架构示例

为了让你彻底理解“双模型”和“多次数据转换”的实战价值，我们来看一个 AIOps 自动排障告警的经典例子。

在这个场景中，用户输入一段混乱的系统日志，我们希望 AI 先提取关键错误，再检索解决方案，最后生成中文修复报告。

案例：告警日志自动化处理链

这个链条包含 2 个模型 和 4 次关键的数据转换。

1. 链条逻辑编排

Python

# 核心逻辑伪代码
chain = (
    # 第一次转换：提取原始日志中的 Error Code
    {"error_code": model_small | JsonOutputParser()} 
    
    # 第二次转换：根据 Error Code 去数据库检索文档
    | {"context": lambda x: retriever.invoke(x["error_code"]), "original_input": RunnablePassthrough()}
    
    # 第三次转换：将文档和原始问题喂给大模型
    | prompt_expert | model_large 
    
    # 第四次转换：将 AI 的 Message 对象转为纯文本
    | StrOutputParser()
)

2. 为什么要这么拆？（数据流转笔记）

步骤组件数据形态的变化 (Transformation)为什么要这么做？
步骤 1小模型 (Qwen-Turbo)非结构化日志 -> {"code": "ERR_001"}精准提取。直接拿万字日志去搜数据库太吵了，先让小模型把“病根”抠出来。
步骤 2Retriever (检索器)ERR_001 -> [K8s 官方修复文档]降噪。只用错误码去搜，搜到的内容比用整段日志搜要准得多。
步骤 3大模型 (Qwen-Max)文档 + 日志 -> 分析报告深度推理。大模型通过阅读文档，结合日志，给出一份逻辑严密的专家建议。
步骤 4OutputParserAIMessage 对象 -> 纯文本字符串最终交付。把模型生成的元数据去掉，只给运维人员看结论。

3. 这里的“双模型”优势

  • 省钱又省时：第一步提取错误码不需要很强的逻辑，用几分钱一度电的小模型就行；最后一步需要“专家级”分析，才动用昂贵的大模型。
  • 高可靠性：如果第一步小模型没提取出错误码，我们可以直接报错，而不必浪费 Token 去跑后续昂贵的大模型。

“避坑”深度思考

你在看这种复杂链条时，只要记住：每一个 | 后面，都是在对数据进行“整容”。

  • 有时候是为了把大象装进冰箱（数据压缩）。
  • 有时候是为了把中文翻译成代码（格式转换）。

你现在的 rag_chain 其实已经具备了这个潜质。 你想尝试把你的 rag_chain 升级一下吗？ 比如：加一个“意图识别”的小模型，如果用户只是在打招呼，直接回“你好”，不触发昂贵的向量数据库检索。这种“按需分配资源”的写法能让你的 AIOps 平台运行效率提升一倍。你要试试看怎么写这个判断逻辑吗？
