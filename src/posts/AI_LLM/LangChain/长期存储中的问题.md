# JSON存储中的问题

在实现 **LangChain 持久化记忆（FileChatMessageHistory）** 的过程中，你遇到了一系列非常经典且具有代表性的“坑”。这些错误本质上都指向了 LangChain **LCEL（表达式语言）** 的核心机制：**数据的显式流动与键值对（Key-Value）的一致性**。

以下是为你整理的避坑总结与核心笔记：

## 1. 核心报错排障笔记

| **错误信息**                                                 | **报错原因 (根源)**                                          | **解决对策**                                                 |
| ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **`The input to RunnablePassthrough.assign() must be a dict.`** | 管道接收到了字符串，但 `RunnableWithMessageHistory` 要求输入必须是**字典**（以便它往里塞历史记录）。 | 在调用 `.stream()` 或 `.invoke()` 时，明确传入 `{"input": user_input}`。 |
| **`VectorStoreRetriever object has no attribute 'get_relevant_documents'`** | **API 版本过时**。新版 LangChain 统一了接口，删除了旧函数。  | 将 `.get_relevant_documents()` 统一替换为 **`.invoke()`**。  |
| **`Input to ChatPromptTemplate is missing variables {'input'}`** | **键值对不匹配**。Prompt 模板里挖了 `{input}` 的坑，但你传进去的字典键名是 `question`。 | 确保 **Prompt 变量名、Chain 的 Key、输入字典的 Key** 三者完全一致。 |
| **`KeyError: 'input'` (Tracer Error)**                       | LangChain 内部监控插件默认寻找 `input` 键，找不到时会报警告。 | 建议将输入变量名统一规范为 **`input`**，或者关闭追踪功能。   |

------

## 2. LCEL 架构下的数据流向图

理解数据是怎么跑的，你就再也不会在变量名上栽跟头：

1. **用户输入**：`{"input": "你是谁"}`
2. **记忆包装器**：自动查 JSON 文件，把历史存入 `{"chat_history": "..."}`。
3. **合并字典**：此时数据变为 `{"input": "...", "chat_history": "..."}`。
4. **自定义逻辑**：通过 `lambda` 提取 `input` 去搜 `context`。
5. **最终字典**：`{"context": "...", "input": "...", "chat_history": "..."}`。
6. **Prompt 填坑**：把这三个值填入模板中对应的 `{}` 占位符。

------

## 3. 持久化存储 (File Storage) 的实战笔记

- **Session ID 的妙用**：通过 `session_id` 可以实现“一人一档”。在 AIOps 场景中，你可以为不同的故障 ID（如 `Issue-20240321`）创建独立的存储文件，实现排障上下文隔离。
- **JSON 文件结构**：`FileChatMessageHistory` 存储的是标准化的 JSON 数组，包含 `type` (human/ai) 和 `content`。这非常利于你后期做**故障复盘分析**——直接把 JSON 喂给分析工具即可。
- **清理机制**：长期存储会导致 JSON 文件过大。在生产环境下，需要手动实现一个“滚动窗口”，比如只保留最近 10 条，或者定期清理 30 天前的旧 Session。
