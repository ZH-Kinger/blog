# 动态入库项目

这张架构图清晰地展示了你的 AIOps 助手如何实现**“动态知识入库”**。

简单来说，它描述了：**用户在网页上上传一个文件，系统如何判断这个文件是否处理过，并最终把它存进向量数据库的完整过程。**


我们可以按照数据的流动方向，把这个过程拆解为三个阶段：

------

## 1. 网页前端阶段：文件的“接收站”

**（对应图中左侧 `app_file_upload.py` 部分）**

- **动作**：用户在 Web 页面点击上传按钮。
- **技术实现**：使用 **Streamlit** 框架。`st.file_uploader()` 负责弹窗和接收文件，`get_value()` 获取文件内容。
- **状态保持**：通过 `st.session_state` 实例化一个 `KnowledgeBaseService` 对象。这样做是为了保证用户在刷新页面时，后台的处理服务不会中断。

------

## 2. 安全检查阶段：MD5 “去重机制”

**（对应图中右上角红色方框部分）**

这是你架构中非常聪明的一点：**防止重复建设**。

- **逻辑**：系统不会盲目地把文件存入数据库，而是先算一下文件的“指纹”（MD5 值）。
- **三个函数**：
  1. `get_string_md5(str)`：把文件内容转换成唯一的 MD5 字符串。
  2. `check_md5()`：去 `md5.txt` 这个“黑名单/白名单”里查一下，这个文件以前传过吗？
  3. `save_md5()`：如果是新文件，处理完后把指纹存下来，下次就不重复处理了。

------

## 3. 后端处理阶段：向量化入库

**（对应图中右侧 `knowledge_base.py` 部分）**

这是 **RAG 架构** 的核心入库逻辑：

- **`self.spliter`**：切分器。把上传的长文档切成 500 字左右的小碎块，防止 AI “噎住”。
- **`upload_by_str()`**：这是核心方法。它接收文件内容和文件名，调用 Embedding 模型，把文字变成坐标。
- **`self.chroma`**：最终的目的地——**Chroma 向量库**。数据被持久化存储在这里，供后续对话时检索。

------

## “架构师”总结

这张图描述的是一个典型的 **“非阻塞式”知识更新流**：

1. **用户视角**：上传文件 -> 看到成功提示。
2. **系统视角**：校验指纹 -> 文本切分 -> 向量编码 -> 存入数据库 -> 记录指纹。

------

## 总结

**这张图做的是“知识入库的自动化与去重”。** 它的存在保证了你的 AIOps 助手能通过 Web 界面随时“学习”新的运维手册，且不会因为重复上传同一个文件而导致数据库臃肿。
