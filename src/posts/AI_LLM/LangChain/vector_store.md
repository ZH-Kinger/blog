# vector_store

在 AIOps 助手这个项目中，**向量存储（Vector Store）** 是实现“私有知识库”的核心组件。它解决了大模型（LLM）最大的两个痛点：**没见过你的内部文档** 以及 **容易胡说八道（幻觉）**。

我们可以从“存储原理”、“检索逻辑”和“在你的代码中如何体现”三个维度来详细拆解。

------

## 1. 存储原理：从文字到“空间坐标”

计算机无法直接理解“K8s 报错”和“容器故障”是相关的。向量存储的核心技术是 **Embedding（嵌入）**。

- **向量化**：Embedding 模型会将每一段运维文档（Document Chunk）转换成一串固定长度的数字，例如 `[0.1, -0.5, 0.8, ...]`。
- **空间意义**：这串数字实际上是多维空间里的一个**坐标**。意思相近的句子，在这个空间里的距离就会非常**近**。

------

## 2. 检索逻辑：语义匹配 vs 关键词匹配

这是向量存储最神奇的地方。它不是在“搜单词”，而是在“搜意思”。

| **维度**     | **传统数据库 (如 MySQL)**    | **向量数据库 (如 Chroma)**         |
| ------------ | ---------------------------- | ---------------------------------- |
| **匹配方式** | 关键词完全匹配（Like %...%） | **语义相似度匹配**（余弦相似度）   |
| **搜索内容** | 必须输入正确的“报错代码”     | 输入“Pod 起不来”，能搜到“容器挂起” |
| **结果返回** | 找到就返回，找不到就为空     | 返回**最像**的那几个片段（Top K）  |

**检索过程：**

1. 用户提问：“Kafka 堆积了。”
2. 系统把这个问题也转换成一个**向量坐标**。
3. 向量数据库计算这个坐标附近有哪些文档片段。
4. 把离得最近的 3 条（k=3）抓出来给 AI。

------

## 3. 在你的代码结构中，它是如何流转的？

在你的模块化架构里，向量存储分为“写”和“读”两个过程：

#### A. “写”过程（在 `ingest.py` 中）

当你运行入库脚本时，发生的是 **ETL（抽取、转换、加载）**：

1. **Load**: `DirectoryLoader` 读取 `data/` 下的文件。
2. **Split**: `RecursiveCharacterTextSplitter` 把长文切成 500 字的小块。
3. **Store**: `Chroma.from_documents` 调用 Embedding 模型把小块变向量，并存入 `vector_db` 文件夹。

#### B. “读”过程（在 `utils/vector_store.py` 中）

当你运行 `app.py` 对话时，它处于**检索阶段**：

1. **Connect**: `Chroma(persist_directory=...)` 像打开 U 盘一样连接到已存好的数据库。
2. **As Retriever**: `.as_retriever(search_kwargs={"k": 3})` 把它变成一个“搜索工具”，随时等待 `rag_chain` 的调用。

------

## 4. 关键参数：什么是 `k` 和 `persist`？

- **`k=3`**: 这代表“只取前 3 名”。如果你设得太小，AI 可能参考资料不足；设得太大，会把无关内容也塞给 AI，浪费 Token 且干扰判断。
- **`persist_directory`**: 这是**持久化**。它确保你的向量数据存进了硬盘。如果没有这一步，程序一关，你辛苦存入的向量就全丢了。

------

## 架构师笔记

1. **模型一致性（致命坑）**：你存的时候用的是 `shibing624/text2vec-base-chinese`，取的时候**必须**也是它。如果换了模型，坐标系就全乱了，AI 会找回一堆乱七八糟的废话。
2. **数据冗余**：Chroma 默认是不去重的。如果你反复运行 `ingest.py`，数据库里会有很多重复片段，这会降低检索效率。

------

## 总结

**向量存储 = AI 的“开卷考试资料”。** 它让 AI 能够在一秒钟内，从数万字的手册里翻到最相关的那三五行字，从而给出准确的运维建议。
