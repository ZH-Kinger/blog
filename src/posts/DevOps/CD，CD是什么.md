# CI/CD

简单来说，**CI/CD 是现代软件开发的一套“自动化流水线”**。

在没有 CI/CD 的年代，程序员写完代码要手动编译、手动测试、再手动上传到服务器，最后祈祷它能跑起来。而 CI/CD 的出现，就是为了让这些“脏活累活”全部由机器自动完成。

------

## 什么是 CI/CD？

CI/CD 实际上由三个部分组成：**持续集成 (CI)**、**持续交付 (CD)** 和 **持续部署 (CD)**。

## 1. CI：持续集成 (Continuous Integration)

**核心思想：频繁合并，及早测试。**

- **流程**：开发者提交代码到仓库（如 GitHub/GitLab）。
- **动作**：系统自动触发**构建**（打包成镜像或二进制文件）和**单元测试**。
- **目的**：确保新加的代码没有把老功能搞坏。如果代码有错，流水线会立刻“报错”，让开发者在错误酿成大祸前修复。

## 2. CD：持续交付 (Continuous Delivery)

**核心思想：代码随时可以发布，但“开关”在人手里。**

- **流程**：代码通过了 CI 阶段的所有测试。
- **动作**：自动将代码发布到测试环境（Staging）或预发布环境。
- **目的**：确保代码在类似生产的环境中也能正常跑。但最后“推送到生产环境”这一步，通常需要人工点一下确认。

## 3. CD：持续部署 (Continuous Deployment)

**核心思想：全程自动化，代码直接上线。**

- **流程**：这是持续交付的“完全体”。
- **动作**：只要代码通过了所有自动化测试，系统就会**直接**把它部署到生产环境，不需要人工干预。
- **目的**：实现真正的快速迭代。

------

## CI/CD 流水线的四个阶段

| **阶段**          | **动作内容**                           | **产出物**      |
| ----------------- | -------------------------------------- | --------------- |
| **代码 (Code)**   | 开发者编写并 Push 代码到 Git 仓库      | Git Commit      |
| **构建 (Build)**  | 编译代码、下载依赖、打包成 Docker 镜像 | Docker Image    |
| **测试 (Test)**   | 运行单元测试、集成测试、代码质量扫描   | Test Report     |
| **发布 (Deploy)** | 将镜像发布到 K8s 集群或服务器上        | Running Service |

------

## 为什么 CI/CD 这么重要？

> “如果你不自动化，你就是在浪费时间修复那些本可以避免的错误。”

- **更快的发布频率**：每天可以发布 10 次甚至 100 次，而不是一个月一次。
- **更低的风险**：通过自动化测试，大部分 Bug 会在进入生产环境前被拦住。
- **标准化**：部署流程变成了 YAML 脚本，不再依赖某个运维大牛的操作习惯。

------

## 主流工具盘点

目前市面上最火的工具主要有三类：

1. **公有云首选**：**GitHub Actions** (简单、直接集成在 GitHub 里)。
2. **企业内网主流**：**GitLab CI** (与 GitLab 深度集成) 或 **Jenkins** (老牌、插件多，但配置略复杂)。
3. **K8s 黄金搭档**：**ArgoCD** (基于 GitOps 理念，专门为 Kubernetes 设计)。
