# 遇到的问题

这次排障是一次非常硬核的 **Kubernetes 全栈网络调优实战**。你从最表层的应用报错，一路深入到了 Linux 内核的路由转发机制。

以下是对这次“填坑之旅”的完整复盘总结：

------

## 一、 遇到问题：故障现象

你最初的目标是实现 **Ingress 金丝雀发布**，但在部署 `ingress-nginx` 时遇到了以下连锁反应：

1. **应用层**：`ingress-nginx-controller` 频繁重启（`CrashLoopBackOff`），报错缺少证书文件。
2. **逻辑层**：负责生成证书的 Job `ingress-nginx-admission-create` 状态一直是 `Running` 但不完成，日志显示 `i/o timeout`。
3. **网络层**：Pod 无法访问集群内部的 API Server（`10.96.0.1`），即便宿主机物理网络是通的。
4. **环境层**：国内镜像站 403 导致镜像拉取困难，宿主机 DNS 偶尔解析失败。

------

## 二、 排查方案：由表及里

我们采取了“剥洋葱”式的排查策略：

| **步骤**            | **动作**                              | **发现的线索**                                        |
| ------------------- | ------------------------------------- | ----------------------------------------------------- |
| **1. 日志分析**     | `kubectl logs`                        | 发现 Job 卡在 `GET Secret`，Controller 卡在证书挂载。 |
| **2. 资源清理**     | `kubectl delete validatingwebhook...` | 排除 Webhook “死锁”导致的 API Server 响应阻塞。       |
| **3. 链路测试**     | 宿主机 `curl` 和 `ping`               | 证明物理网络 OK，但 Pod 虚拟网络不通。                |
| **4. CNI 深度检查** | `calico-node -show-status`            | 证明 BGP（控制面）正常，但数据面丢包。                |
| **5. MTU 验证**     | `ping -M do -s 1472`                  | 排除由于 IPIP 封包过大导致的路径 MTU 限制。           |
| **6. 内核参数检查** | `sysctl -a | grep rp_filter`          | **抓到真凶**：内核开启了严格的反向路径过滤（RPF）。   |

------

## 三、 解决办法：三步走

为了彻底修复问题，我们执行了以下操作：

## 1. 紧急规避（应急方案）

- **动作**：在 Deployment 中开启 `hostNetwork: true`。
- **原理**：让 Pod 直接绕过 CNI 虚拟网络，借用物理网卡通讯，快速打通业务。

## 2. 根因修复（永久方案）

- **动作**：在所有节点执行 `sysctl -w net.ipv4.conf.all.rp_filter=0`。
- **原理**：关闭 Linux 内核的严格校验模式。由于 Calico IPIP 模式下，包是从隧道口（`tunl0`）进来的，但回程路由指向物理口，`rp_filter=1` 会误以为这是“欺骗包”并丢弃。

## 3. 环境适配

- **动作**：使用本地已有镜像（`IfNotPresent`）或镜像代理加速。
- **结果**：解决了镜像拉取失败导致的 `ImagePullBackOff` 问题。

------

## 四、 核心知识点总结

通过这次实验，你掌握了以下高阶运维技能：

- **Ingress 原理**：理解了 Admission Webhook、Secret 与 Controller 的依赖关系。
- **Calico 网络模型**：理解了 **BGP（路标）** 与 **IPIP 隧道（车辆传输）** 的区别。
- **Linux 内核网络**：学会了如何调整 `rp_filter` 和 `ip_forward` 来适配容器网络。
- **HostNetwork 模式**：掌握了在 CNI 故障时，如何通过改变网络命名空间进行紧急抢修。

------
