# 灰度发布

## 一、 灰度发布（Canary Release）标准流程

灰度发布的核心逻辑是：**在生产环境同时运行旧版本（Stable）和新版本（Canary），通过控制流量比例，让一小部分用户先试用新功能，确保没问题后再全量上线。**

1. **版本准备**：准备好两个版本的代码/镜像（v1 和 v2）。
2. **环境部署**：在集群中同时部署两套 Deployment 和对应的 Service。
3. **流量分流**：配置 Ingress，通过 `Annotations`（注解）定义分流规则（如权重、Header 或 Cookie）。
4. **观测验证**：监控新版本的错误率、延迟、资源消耗等指标。
5. **最终决策**：
   - **成功**：将旧版本流量全部切换至新版本，删除旧版本。
   - **失败**：修改 Ingress 规则，将流量瞬间切回旧版本（回滚）。



## 二、 你的实战记录：从“填坑”到“通关”

你的操作比普通实验要复杂得多，因为你经历了完整的**故障排查（Troubleshooting）**过程。

## 1. 业务逻辑配置（常规部分）

- **内容区分**：利用 **ConfigMap** 挂载不同的 `index.html`，分别代表 v1（稳定版）和 v2（灰度版）。
- **服务部署**：创建了两个 Service：`web-v1` 和 `web-v2`。
- **Ingress 规则**：
  - 创建了一个主 Ingress 指向 v1。
  - 创建了一个特殊的 **Canary Ingress**，通过注解 `nginx.ingress.kubernetes.io/canary: "true"` 和 `canary-weight: "20"` 将 20% 的流量导向 v2。



### 配置文件web-v1

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-html-config
data:
  index.html: |
    <!DOCTYPE html>
    <html>
    <head><meta charset="UTF-8"><title>K8s Nginx 测试</title></head>
    <body>
        <h1>?? 恭喜！Nginx 内容修改成功</h1>
        <p>这是通过 ConfigMap 挂载到 Pod 中的自定义页面。</p>
        <hr>
        <p>当前版本：v1 (Managed by Deployment)</p>
    </body>
    </html>
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-v1
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
      version: v1
  template:
    metadata:
      labels:
        app: web
        version: v1
    spec:
      containers:
      - name: nginx
        image: nginx:1.20
        ports:
        - containerPort: 80
        volumeMounts:
        - name: html-volume
          mountPath: /usr/share/nginx/html/index.html
          subPath: index.html
      volumes:
      - name: html-volume
        configMap:
          name: web-html-config

```





### 灰度发布配置

```
# ingress-canary.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-canary
  annotations:
    kubernetes.io/ingress.class: nginx
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20" # 20% 的流量分给 v2
spec:
  rules:
  - host: myweb.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-v2-svc
            port:
              number: 80
```





### 主入口配置文件

```
# ingress-stable.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-stable
  annotations:
    kubernetes.io/ingress.class: nginx
spec:
  rules:
  - host: myweb.com  # 假设你的域名
    http:
      paths:
      - path: /
        pathType: Prefix

            name: web-v1-svc
            port:
              number: 80
```

##  基础设施类：Ingress 控制器

这是你从 GitHub 或是官方下载的那一大串 YAML（通常叫 `deploy.yaml`）。

- **Deployment (`ingress-nginx-controller`)**：这是“大脑”，负责接收外部流量并根据规则转发。你之前在这里改了 `hostNetwork: true` 来绕过 CNI 故障。
- **Job (`ingress-nginx-admission-create/patch`)**：这是“临时工”，专门负责生成 HTTPS 证书。之前就是它因为网络不通报了 `i/o timeout`。
- **Service (`ingress-nginx-controller-admission`)**：给控制器自己用的内部通讯接口。

------

##  业务内容类：你的 Web 应用

这部分是你为了测试金丝雀发布自己定义的。

- **ConfigMap (`web-html-v1-config` / `v2`)**：这是“内容库”。你把两个版本的 HTML 页面塞在这里，实现了“不改镜像只改网页”的效果。
- **Deployment (`web-v1` / `web-v2`)**：这是“容器组”。它们挂载了上面不同的 ConfigMap，一个显示“版本 v1”，一个显示“版本 v2”。
- **Service (`web-v1-svc` / `web-v2-svc`)**：这是“内部地址”。它们给 Pod 起了个固定的名字，让 Ingress 能找到它们。

------

## 流量调度类：Ingress 路由规则

这是实现“20% 流量给 v2”的核心魔术。

- **Ingress (`web-ingress-main`)**：这是“主入口”。它定义了域名（比如 `myweb.com`）默认指向 `web-v1`。
- **Ingress (`web-ingress-canary`)**：这是“灰度入口”。
  - 它多了一行关键的 **Annotations（注解）**：`nginx.ingress.kubernetes.io/canary: "true"`。
  - 还有权重设置：`canary-weight: "20"`。

------

## 网络底层类：Calico 配置（隐藏的 YAML）

虽然你主要是通过 `kubectl patch` 或 `sysctl` 修改的，但它们本质上改变了 CNI 的运行逻辑。

- **Installation / IPPool**：定义了 Pod 的 IP 段以及是否开启 **IPIP 模式**。
- **FelixConfiguration**：控制着节点上的路由转发行为（包括你折腾半天的 BGP 状态）。

------

## 总结：流量是怎么走的？

1. **用户**：访问 `http://192.168.245.145` (Node-2 的 IP)。
2. **内核**：发现 Ingress Controller 占用了 80 端口（因为你开了 `hostNetwork`），把包丢给控制器。
3. **Ingress Controller**：看一眼域名和路径，发现有“金丝雀”规则。
4. **随机分流**：根据 20% 的概率，决定把包甩给 `web-v1-svc` 还是 `web-v2-svc`。
5. **Pod 回应**：对应的 Pod 从挂载的 **ConfigMap** 里读出 HTML，返回给用户。
