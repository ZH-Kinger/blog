# 研发自动化协作平台 — 开发 Story

**项目代号**：wuji-agent | **版本**：v1.0 | **更新日期**：2026-04-27

---

## 一、背景与目的

研发团队 PR 流程缺乏统一规范，代码审查依赖人工，Jira 工单和飞书通知全靠手动，效率低且容易遗漏。

目标：
- PR 提交后自动完成规范检查、AI 审查、Jira 建单、飞书通知
- 审核人只需关注最终审批，其余环节全自动
- 统一仓库接入方式，降低各业务仓库的接入成本

---

## 二、需求分析

| 场景 | 当前问题 | 期望行为 |
|------|---------|---------|
| PR 规范 | 标题格式和工作项引用全靠人工检查 | CI 自动校验，不合规直接失败 |
| 代码审查 | 依赖人工，响应慢 | AI 自动 Review 并评论到 PR |
| Jira 建单 | 手动创建，经常遗漏 | PR 无 Jira ID 时自动建单 |
| 飞书通知 | 无通知，审核人不知道有 PR 待审 | Review 完成后自动推送卡片并 @ 审核人 |
| 仓库接入 | 每个仓库手动配置 workflow | 两行命令完成接入 |

### 目前存在的问题

1. 飞书审核人 open_id 使用占位值，通知无法实际送达
2. 无 HTTPS，Token 存在明文传输风险
3. Release 自动化流程未实际触发验证过
4. 无结构化日志，排障依赖 print
5. Redis 无持久化配置，容器重启后缓存丢失

## 三、Story 列表

### Phase 1 — 核心 Pipeline（P0）

| ID | Story | 优先级 | 验收标准 |
|----|-------|--------|---------|
| S-01 | 开发者提交 PR 时，标题格式和 Jira ID 引用全靠人工检查，不合规的经常到了审核阶段才被指出，来回修改效率低。我们希望在 CI 阶段自动拦截，把规范问题消灭在审核人看到之前。 | P0 | 标题不符合 `type(scope): description` 格式时，CI Check 失败；缺少 Jira ID 时 CI Check 失败；格式合规时 CI 全部通过 |
| S-02 | 目前代码审查全靠人工，审核人需要逐行阅读代码，耗时长且容易遗漏潜在风险。引入 AI 自动 Review 后，审核人在人工审核前就能先拿到风险摘要和改进建议，把精力放在关键决策上。 | P0 | AI Review 评论成功发布到 PR 页面；评论包含风险提示和改进建议；同一 PR 不重复发评论 |
| S-03 | 经常有 PR 忘记关联 Jira 工单，导致发版时追溯不到变更来源。我们希望在 PR 没有 Jira ID 时自动兜底建单，并把编号回写到 PR，确保所有代码变更都有迹可循。 | P0 | PR 描述无 Jira ID 时，自动创建 Jira 工单并将工单号回写到 PR；已有 Jira ID 时不重复创建 |
| S-04 | 团队目前靠手动刷 GitHub 看 PR 进展，信息不同步，审核人经常不知道有新 PR 待审。Review 完成后自动推送到飞书群，大家不用切平台就能同步状态。 | P0 | Review 完成后，飞书群消息卡片成功送达；卡片包含 PR 链接、Review 摘要 |

### Phase 2 — 安全加固与通知链路（P1）

| ID | Story | 优先级 | 验收标准 |
|----|-------|--------|---------|
| S-05 | 飞书群通知是广播式的，审核人容易被大量消息淹没，漏掉需要自己处理的 PR。我们希望支持 @ 指定审核人推送个人消息，确保每个审核人都能及时收到与自己相关的待审提醒。 | P1 | @ 审核人的消息成功送达个人会话；消息包含 PR 链接和关键摘要 |
| S-06 | 目前 Token 是全局共用的，一个仓库泄露可能影响所有仓库，且 Redis 重启后配置会丢失。我们希望每个仓库拥有独立的 Token，持久化存储，实现权限隔离，降低单点泄露风险。 | P1 | 不同仓库的 `wr_xxx` Token 互不生效；Redis 重启后 Token 仍可读取 |
| S-07 | 新仓库接入 PR Pipeline 需要手动复制 workflow 文件、改环境变量、配 Secret，步骤多容易出错，业务团队上手成本高。我们希望做到 `wuji-review init` 两行命令完成接入，让业务仓库也能自助完成。 | P1 | 执行命令后仓库自动生成 PR workflow 文件；首次提交 PR 时 CI 正常触发 |
| S-08 | 目前 main 分支缺少强制保护，存在未经审核直接合入的风险。我们希望配置分支保护规则，main 合入必须满足至少 1 人 Approve 且 CI 通过，保障主干代码质量。 | P1 | main 分支保护规则生效；无 Approve 或 CI 失败时，合并按钮禁用 |
| S-11 | 目前服务端通信存在明文传输风险，Token 和敏感数据可能被中间人截获。我们希望全链路启用 HTTPS，包括 Nginx 反代、客户端到服务端、服务端到 GitHub API，满足基础安全合规要求。 | P1 | Nginx 反代配置 SSL；前端/CLI 到服务端、服务端到 GitHub API 均走 HTTPS |

### Phase 3 — 工具扩展与发布自动化（P2）

| ID | Story | 优先级 | 验收标准 |
|----|-------|--------|---------|
| S-09 | 目前 MCP 工具只能在本地 IDE 中使用，使用 Claude Code 的开发者无法远程调用平台能力。我们希望支持通过 SSE 远程连接，让本地 IDE 之外的场景也能使用 Review、建单等工具。 | P2 | Claude Code 通过 SSE 成功连接；工具调用返回预期结果 |
| S-10 | 目前发版需要手动推断版本号、写 CHANGELOG、创建 Release PR，步骤繁琐容易出错。我们希望根据 Commit 历史自动推断版本、更新 CHANGELOG 并创建 Release PR，减少人工操作，规范发版流程。 | P2 | 版本号推断正确（major/minor/patch）；CHANGELOG 自动更新；Release PR 自动创建 |
| S-12 | 目前系统日志格式不统一，排障时靠 print 和手动 grep，效率低且难以追溯。我们希望输出统一格式的结构化日志，包含 trace_id、耗时、状态码等关键字段，提升故障定位效率。 | P2 | 关键操作（Review、建单、通知）均有结构化日志；日志包含 trace_id、耗时、状态码 |

## 六、风险与依赖

| 风险项 | 影响 | 缓解措施 |
|--------|------|---------|
| 无 HTTPS | Token 明文传输，安全风险 | 配置 Nginx 反代 + SSL |
| Redis 无持久化 | 重启后 Token / 审核人配置丢失 | 配置 AOF 持久化 |
| Release PR 用个人 PAT 创建 | 不符合组织审计要求 | 后续迁移到 GitHub App |
| 服务无监控 | 挂掉无感知 | 接入飞书告警或 Prometheus |
