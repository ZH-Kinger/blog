欢迎来到智算中心的“地下室”——**裸金属与 GPU 硬件层**。

在这一层，我们不关心跑的是 Qwen 还是 LLaMA，也不关心 K8s 的 Pod 怎么调度。我们只关心一件事：**这台价值几百万的物理服务器（比如你的 HGX H200），它的供电、散热、以及 PCIe 总线是否能支撑住长达几个月的暴力轰炸。**

如果把 AI 训练比作赛车，这里就是监控发动机温度、机油压力和轮胎磨损的仪表盘。

为了让你直观感受这一层监控的实战压迫感，我为你搭建了这个“HGX 物理节点硬件灾难级监控沙盒”。你可以亲自触发一些硬件故障，看看不同探针（Exporter）是如何联动报警的：

### 🛠️ 第一层实战指南：部署你的“三大金刚”探针

在真实的物理机房里，你需要在每一台服务器的宿主机操作系统（通常是 Ubuntu 22.04）上，部署三个守护进程。它们是整个 AIOps 数据链路的源头。

#### 1. GPU 的绝对主宰：`dcgm-exporter`

这是英伟达官方出品的探针，直接读取 GPU 寄存器。不要再用 `nvidia-smi` 写死循环脚本了，那个极度消耗性能且获取的数据太浅。

你在 Grafana 里配置 Prometheus 查询（PromQL）时，必须死盯以下几个核心指标：

- **温度与降频防线：**
- `DCGM_FI_DEV_GPU_TEMP` (核心温度)
- `DCGM_FI_DEV_SM_CLOCK` (SM 实际频率)
- *实战逻辑：* 设定报警规则：一旦温度超过 80 度且 Clock 频率相比基准线下降超过 10%，立刻触发飞书最高级别告警（P0）。这意味着机器正在默默吞噬算力。
- **硬件 ECC 纠错拦截：**
- `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL` (双位错误)
- *实战逻辑：* HBM3 显存在高压下极易发生比特翻转。如果发生 DBE（双位不可纠正错误），GPU 会直接挂死（Xid 报错）。监控这个指标能让你在显卡彻底报废前联系原厂保修。

#### 2. 宿主机的管家：`node_exporter`

很多人以为搞大模型只要盯着 GPU 就行了，这是巨大的误区。当你的 CPU 被塞满，或者 NVMe 硬盘的 I/O 队列被打爆时，GPU 就会沦为一块极其昂贵的废铁。

- **CPU 偷窃与等待 (Steal & IOWait)：**
- 监控 `node_cpu_seconds_total{mode="iowait"}`。如果这个值飙升，说明 CPU 在发呆等硬盘读数据。这通常发生在读取海量小图片（如机器狗视觉预训练）时。
- **PCIe 拓扑瓶颈：**
- 这虽然不直接暴露在 Node Exporter，但需要结合系统日志。一台 HGX 服务器里有复杂的 PCIe Switch。如果网卡和 GPU 没有插在同一个 NUMA 节点上，数据就会跨越 QPI 总线，导致延迟飙升。

#### 3. 最后的救命稻草：带外管理 (IPMI / Redfish)

假设机器彻底死机了，连 SSH 都连不上，`node_exporter` 进程也死了，你怎么知道机房发生了什么？

- **物理底盘监控：** 每台服务器的主板上都有一个独立的小芯片（比如戴尔的 iDRAC 或浪潮的 BMC）。它有自己独立的网口。
- 通过拉取 IPMI 指标，即使服务器关机，你也能知道电源模块（PSU）的输入电压是多少、12 个暴力风扇分别转速是多少。这往往能提前几小时预警机房的断电或精密空调失效。

### 🚀 下一步你的行动规划

如果你要在你们的集群里落地第一层监控，通常的架构动作是：

1. 写一个 Ansible Playbook，批量在 32 台机器上安装 `dcgm-exporter` 和 `node_exporter`，配置它们对外暴露 `9400` 和 `9100` 端口。
2. 在一台独立的监控机上拉起 Prometheus，去抓取这 32 台机器的数据。

这一层的监控是纯粹的物理防御。你现在是打算直接去集群里跑几条 Ansible 命令把探针装起来看一眼真实数据，还是继续向上一层（网络与存储层）进发，看看 RDMA 是怎么被监控的呢？
